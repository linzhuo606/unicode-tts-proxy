# Unicode 朗读中转

一个 Android 语音引擎。它自己不发声，而是先把文本里读不出来的字符换成中文，
再交给你自己选的语音引擎去念。

## 它解决什么问题

很多商业语音引擎对 Unicode 的处理不完善：emoji、数学符号、物理化学符号会被读错、
读成乱码，或者干脆没有声音。对依赖读屏的用户来说，这不是体验问题，而是**信息直接丢失**
——数学题里的 ∑ ∫ ²、化学式里的 H₂O SO₄²⁻ ⇌、聊天里的表情，读不出来就等于看不见。

装上之后：

| 原文 | 处理前（常见表现） | 处理后 |
|---|---|---|
| `已完成👍` | 「已完成」，表情被跳过 | 已完成 拇指向上 |
| `👨‍👩‍👧‍👦` | 静音，或把连接符读成问号 | 家庭 |
| `SO₄²⁻` | 「S O 4」 | SO 下标 4 二价负 |
| `温度 25℃，面积 100㎡` | 「温度 25，面积 100」 | 温度 25 摄氏度，面积 100 平方米 |
| `𝐀𝐁𝟏𝟐` | 静音或乱读 | AB12 |
| `ℝ 上的连续函数` | 「上的连续函数」 | 实数集 上的连续函数 |
| `①第一条` | 「第一条」 | 带圈 1 第一条 |
| `⠁⠃⠉`（盲文点位） | 静音 | 点 1 点 1 2 点 1 4 |
| `10Ω` / `角频率Ω` | 「10」/「角频率」 | 10 欧姆 / 角频率 欧米伽 |
| `ʃ`（国际音标） | 静音 | 点 1 5 6（详细档再加「清龈后擦音」）|
| `🌚` | 「微笑的朔月」，听了等于没听 | 黑脸月亮 |
| `🥰` | 「喜笑颜开」，丢了「三颗心」这个关键特征 | 三心笑脸 |

## 安装与首次配置

全程可以只靠听完成。

1. 从 [Releases](https://github.com/linzhuo606/unicode-tts-proxy/releases) 下载最新的
   `unicode-tts-proxy-版本号.apk` 并安装。以后出新版直接覆盖安装，设置和自定义词典都会保留。
2. 打开手机的**设置** → **无障碍** → **文字转语音输出**，把**首选引擎**选成
   「Unicode 朗读中转」。
3. 打开「Unicode 朗读中转」这个应用，在**发声引擎**里选一个真正负责发声的引擎
   （比如你原来一直在用的那个）。选好之后它会朗读一句确认。
4. 需要的话，在**符号朗读详略**里挑一档：
   - **关闭**：不读表情符号（但仍然清理乱码字符）
   - **简洁**（默认）：读简短名称
   - **详细**：读完整描述，包括肤色、性别等修饰

### 怎样换回原来的引擎

打开**设置** → **无障碍** → **文字转语音输出** → **首选引擎**，改回原来的引擎即可。
本应用不会锁定系统设置。

### 如果没有声音

- 应用里的**发声引擎**列表是空的 → 系统里没有别的语音引擎，先装一个。
- 选好引擎后仍然没声音 → 打开**兼容模式**再试。少数第三方引擎不支持默认的取音方式。
- 仍然不行 → 按上一节换回原来的引擎，手机不会一直哑着。

## 工作原理

```
TalkBack / 任意应用
      │  speak("已完成 👍  ΔH = -285.8 kJ")
      ▼
  本引擎：换掉读不出来的字符
      │  speak("已完成 拇指向上  德尔塔 H = -285.8 kJ")
      ▼
  你选的发声引擎  →  扬声器
```

音频用「流式截获」的方式取回：调下游引擎的 `synthesizeToFile()`，靠
`onBeginSynthesis` / `onAudioAvailable` 在合成过程中实时收 PCM，再回灌给系统。
写 WAV 的是 Android 框架自己的代码而不是引擎代码，所以任何标准 TTS 引擎都支持这条路。
这样音量、音频焦点、无障碍音量、打断，全都仍然由系统掌控。

## 仓库结构

```
core/     纯 Kotlin，文本处理的全部逻辑。独立构建，不需要 Android SDK 就能跑测试。
android/  Android 应用。通过 includeBuild("../core") 复合引入 core。
tools/    词典生成器：把 Unicode 官方数据编译成 APK assets 里的 symbols.tsv。
```

`core` 独立成一个构建是有意的：符号读得对不对，是这个项目的主要价值，
应该能在没有安卓设备、没有 Android SDK 的机器上直接验证。

## 构建

三个构建各自带 Gradle wrapper，只需要 JDK 17。

```bash
cd core && ./gradlew test                  # 文本处理的单元测试，不需要 Android SDK
cd android && ./gradlew :app:assembleDebug # 需要 Android SDK
```

产物在 `android/app/build/outputs/apk/debug/app-debug.apk`。

构建 APK 需要在 `android/local.properties` 里指明 SDK 位置（该文件不入库）：

```properties
sdk.dir=C:/Users/你的用户名/android-sdk
```

GitHub Actions 每次推送都会构建一个测试版（Actions 页面里的 `ttsproxy-debug-apk`），
但它的签名每次都不一样，只适合开发者验证。正式版的签名与发布流程见 [docs/RELEASING.md](docs/RELEASING.md)。

### Windows 上 Gradle 报 "Unable to establish loopback connection"

某些安全软件会拦住 `%LOCALAPPDATA%` 目录下的 AF_UNIX 套接字，而 JDK 17 的
`Selector.open()` / `Pipe.open()` 会**先走 AF_UNIX**（走不通也不回退到 TCP）。
现象是 Gradle 连自己的 daemon 都连不上，而普通 TCP 回环其实一直是好的。

把临时目录挪出 `AppData\Local` 即可：

```bash
export TMP='C:\jtmp' TEMP='C:\jtmp'   # PowerShell: $env:TMP='C:\jtmp'; $env:TEMP='C:\jtmp'
```

目录要先建好。**只设 `-Djava.io.tmpdir` 不管用**（实测无效），得改环境变量，
或者直接指定那个专用属性：

```bash
export JAVA_TOOL_OPTIONS='-Djdk.net.unixdomain.tmpdir=C:\jtmp'
```

后一种最稳：它对每个 JVM 都生效，包括 Gradle 自己 fork 出来的 daemon。
写进 `~/.gradle/gradle.properties` 的 `org.gradle.jvmargs` 反而没用——
项目里的 `android/gradle.properties` 会把它整条盖掉。

判断方法：写个只调用 `java.nio.channels.Pipe.open()` 的小程序，打印异常的
`getCause()`。是这个问题的话，根因会是
`java.net.SocketException: Invalid argument: connect`，栈里带 `UnixDomainSockets.connect0`。

## 重新生成词典

```bash
cd tools
./gradlew run --args="data ./data ../android/app/src/main/assets/symbols.tsv"
```

缺失的 Unicode / CLDR 数据文件会自动下载。CLDR 固定在 46.0.0；emoji 序列表取
`/Public/emoji/latest/`（Unicode 只为 16.0 及以前保留版本目录），实际版本号会写进
产物头部。生成物 `symbols.tsv` 是入库的，所以构建本身可复现，重新生成属于维护动作。

## 上下文规则

少数符号在不同语境里读法不同。这里只做**高精度**的几条，取舍原则是
**宁可漏判也不要错判**——读成通用读法只是啰嗦，读错却会误导学生。

| 符号 | 条件 | 读法 |
|---|---|---|
| `Ω` | 前面是数字或 SI 词头（`10Ω`、`4.7kΩ`） | 欧姆 |
| `Ω` | 其他（`角频率Ω`） | 欧米伽 |
| `↑` `↓` | 前面是**带下标数字**的化学式（`CO₂↑`、`BaSO₄↓`） | 气体 / 沉淀 |
| `↑` `↓` | 其他（`GDP↑`、`价格↑`） | 上箭头 / 下箭头 |
| `′` `″` | 前面是拉丁字母（`f′`） | 导数 / 二阶导数 |
| `′` `″` | 前面是数字（`45′`） | 分 / 秒 |
| `μ` | 后面跟单位（`μm`、`μs`） | 微米 / 微秒（整词读出） |
| `μ` | 其他 | 缪 |

化学式判据刻意收紧到「必须出现下标数字」，因此 `AgCl↓` 会漏判读成「下箭头」。
这是有意的：漏判只是啰嗦，把 `GDP↑` 读成「GDP 气体」才是灾难。

`Δ` 在化学方程式里标在箭头上方表示加热，但纯文本里表达不出这个位置关系，
所以不做这条规则，一律读「德尔塔」。

## 数理化与其他符号的读法标准

非 emoji 的功能符号（数学、理化、技术、几何、标点、带圈 CJK）全部用 Opus 5 逐块重写过，
按 Unicode 块切成 60 批，每批一个子代理，回收后过三道机械检查。

判断标准和 emoji 不同：功能符号不承载情绪，用户要的是**快速拿到信息**。所以：

- **有确定含义的读含义，不读字形。** `∀` 读「对任意」不读「倒 A」；`ℝ` 读「实数集」
  不读「双线体 R」；`⇌` 读「可逆」。
- **纯图形读形状。** `▲` 读「实心三角」，`╱` 读「右斜线」。
- **单位读单位本身，且必须准确。** `㎩` 读「帕」，`㎨` 读「米每二次方秒」——
  单位读错会让学生算错题，这一块的核对比别处都严。
- **不认识就描述字形，绝不编造用途。** 编一个听起来专业的假用途，比老实说「一个斜十字」
  有害得多。

### 重名的规矩和 emoji 不一样

emoji 那边是零重名：两个不同的表情读成同一个名字就是信息损失。
功能符号这边放宽了**简洁档**：一族形近的右箭头（`→` `➔` `➜` `➝`）对听的人本来就是一回事，
硬凑十七个不同的名字只会更难记。

但**详细档必须全局唯一**——两个字符在任何档位都听不出区别，那才是真的丢信息。
生成时会全量核对，撞车的自动把简洁读法接到详细读法前面。上一版遗留的问题正是这类：
`❶❷❸` 的详细读法都是「黑底白字的圆圈数字」，`╱`（对角线）和 `╵`（半线）都被读成「竖线」，
这一轮全部修掉了。

### 标点与空白：词典不许插手

`。，、；：？！`、`《》【】〔〕`、各种引号，以及间隔号、省略号、破折号、连接号**都不进词典**，原样交给下游引擎。
它们对下游来说不是要念的符号，而是韵律指令：在哪里停、停多久，中文引擎本来就处理得很好。

这条吃过亏。有一版给「CJK 符号和标点」整块补了读法，`。` 被读成「句号」两个字、`、` 读成「顿号」，
长文朗读当场挤成一团：下游看不到断句，句与句之间不再停顿；分块器也靠句号断句，
一段长文成了一整块，音频撑爆缓冲、开始丢数据——症状和更早一次缓冲丢数据的故障一模一样。

所以现在是两道硬闸：生成词典时收了这些标点直接报错（`GenerateDict`），运行时就算词典里有，
内置条目也一律忽略（`ProsodyPunctuation`）。用户自定义词典不受限制，那是用户自己的选择。
引号同样在这份清单里，见「引号」一节。

同一次还补了两处底层的保险。分块器在句号断不开的长句里改在逗号、顿号处切，
**每一块都保证不超过 250 字**，不再依赖文本里有没有句号；音频管道不再让 binder 线程
等缓冲腾地方——那种「等」其实会把下游的回调堵在内核里，下游那头会悄悄丢音频，
我们这边连计数都看不到。

**空白和格式控制符也一样，一个字都不该念。** 不换行空格（U+00A0，网页里的 `&nbsp;`）、全角空格、
软连字符、零宽空格这些，要么折成普通空格，要么直接去掉，词典不许给它们配读法——词典匹配排在折叠和
清理之前，一旦配了读法就会被念出来。批量补「拉丁补充」那一块时，不换行空格和软连字符就被配上了
「不换行空格」「软连字符」，网页长文里隔几个词就会冒一句。这一条按 Unicode 类别判定（空白、控制、
格式三类），不列清单：清单会漏，类别不会。

### 覆盖情况

按 Unicode 块统计已分配码位的收录率：

| 类别 | 覆盖 |
|---|---|
| 数学（运算符、箭头、类字母、数字形式、上下标、四个补充块） | 100% |
| 理化（希腊字母、CJK 兼容单位、声调修饰字母） | 100% |
| 技术与图形（杂项技术、几何、装饰、方块、制表符、控制图形、OCR） | 100% |
| 标点（通用标点的可见部分、补充标点、竖排形式） | 100%（中文正文标点有意不收，见上） |
| 带圈（字母数字、CJK） | 100% |
| 盲文点字、国际音标 | 100%（音标按 ICEB 范围） |

**有意不收**的几类：ASCII 字母数字（动了就毁掉普通文本）、带附加符号的拉丁字母
（走折叠规则）、西文里的普通字母 `æ ø ß ð þ`（原样交给下游，生成器会拦）、数学字母数字与全角形式（走折叠规则）、空白与格式控制字符
（走空格折叠与不可见字符清理）、西里尔文（不在目标语种内），以及中文正文标点（原样交给下游，见上）。

## emoji 读法的标准

这部分是整个项目里最难定标准的地方。CLDR 官方中文名给的是**画面标签**，而且常常是英文名
直译，比如 🌚 叫「微笑的朔月」——中文里没人这么说，听了也不知道是哪个。

现在**全表 emoji 已按下面的标准重写完毕**——1922 条基础序列，加上机械派生的肤色与
性别变体，覆盖词典里全部 5209 条 emoji。两个档位走**不同的轴**：

| 轮次 | 范围 | 条数 | 方式 |
|---|---|---|---|
| 第一轮 | 脸、手势、身体部位、心形、气泡、月亮脸 | 237 | Opus 5 分批 + 人工校验 |
| 人物家庭 | 家庭组合、发色性别变体、情侣 | 67 | **脚本机械推导**，组成编码在码位序列里 |
| 第二轮 | 手势姿态、奇幻角色、动物、天气植物、食物饮品 | 353 | Opus 5 分批 + 人工校验 |
| 第三轮 | 职业身份、日常动作、体育运动、服装配饰 | 246 | Opus 5 分批 + 人工校验 |
| 第四轮 | 办公文具、家居工具、数码影音、乐器仪器、庆典、体育游戏 | 304 | Opus 5 分批 + 人工校验 |
| 第五轮 | 水生与昆虫、地点建筑、陆海空交通、钟表时刻 | 215 | Opus 5 分批 + 人工校验 |
| 第六轮 | 公共标识、警告禁止、箭头播放键、宗教星座、数字字母方块、几何形状 | 235 | Opus 5 分批 + 人工校验 |
| 国旗 | 259 面国旗与地区旗 | 259 | Opus 5 分批 + 人工校验 |
| 新序列补丁 | Unicode 17.0 的兔耳双人、摔跤 | 6 | **脚本机械推导** |

国旗那一轮的简洁名沿用 Unicode 官方中文国名不动，价值全在详细档——旗面上到底几道条、
什么颜色、什么图案，是盲人无从获得而明眼人一眼就有的信息。


**简洁名（≤6 字）走「明眼人会怎么称呼它」**，因为目的是和对方对得上号——朋友说「我给你发了个
捂脸」，你听到的也得是「捂脸」。判据按优先级：

1. 有公认中文叫法就用它，**对的不要改**（捂脸、笑哭了、点赞本来就对）
2. 没有公认叫法的，用最能辨认的视觉特征造短名（黑脸月亮、三心笑脸、斜眼坏笑）
3. **必须能和相邻 emoji 分开**，同批内不许重名
4. 简洁名不写含义——含义强依赖上下文，写死在词条里本身就是错的

**详细档（≤40 字）走视觉信息**，格式固定 `名字：画面。常表示 X、Y。`

- 画面只说盲人无法自行获得的信息：颜色、朝向、眼眉嘴形态、附加物、数量、手指姿势
- 含义一律用「**常**表示」而不是「表示」
- 粗俗义、讽刺义、性暗示、跨文化差异**如实说明并标出语气**（😏「也作性暗示，慎用」，
  ✌️「掌心朝内在英国属冒犯」）
- **拿不准就只写画面，不许编含义**——读错比不读更糟

### 整段只有一个 emoji 时自动读详细

用 TalkBack 逐字符浏览去查某个 emoji 时，引擎收到的就是单独一个 emoji；别人发来一条纯 emoji
消息也是。这两种情况都是想搞懂它，且不存在刷屏问题，所以直接读详细档。日常读消息仍是短名。
设置里可以关掉这个行为。

### 连续重复

👍 读「点赞」，👍👍 读「点赞 点赞」（保留强调语气），👍👍👍 起才读「3 个 点赞」。

## 国际音标

覆盖范围与 **ICEB IPA Braille**（国际盲文音标）对齐：它收的音标符号我们全收，
点位逐条比对过，141 条全部一致。

| 输入 | 简洁档 | 详细档 |
|---|---|---|
| `ʃ` | 清龈后擦音 | 点 1 5 6 清龈后擦音 |
| `ŋ` | 软腭鼻音 | 点 1 2 4 6 软腭鼻音 |
| `ɖ` | 浊卷舌塞音 | 点 2 5 6 点 1 4 5 浊卷舌塞音 |
| `̃` | 鼻化 | 点 4 点 1 2 4 5 6 鼻化 |

简洁档读**中文音理简称**，详细档读**盲文点位 + 完整音理**。
简称由音理描述按固定规则机械派生，不经模型推断：响音去掉冗余的「浊」
（`ŋ` 是「软腭鼻音」不是「浊软腭鼻音」），「不圆唇」写成「展唇」，
「次闭次前」写成「次闭前」。最长 7 个字，多数在 2 到 6 个字。

### 想直接听点位

设置里有「音标读盲文点位」开关。打开之后简洁档改读点位，`ŋ` 读「点 1 2 4 6」。
详细档不受影响，任何时候都是点位加音理。两种读法对应同一份 ICEB 表，
只是简洁档念哪一面的区别。

多方盲文按方分开读，每方以「点」起头，听感上不会粘连。

### 三类刻意没收，收了会误伤日常文本

- `æ ç ð ø č œ š ž ǰ`：在法语、丹麦语、捷克语里就是字母。收进内置词典的话，
  `façade` 会被读成「fa 清硬腭擦音 ade」。
  **需要与 ICEB 完全对齐时**（比如读音标教材），在自定义词典界面导入
  `tools/data/ipa-letters.tsv` 即可补齐这 9 条；不想要了逐条删掉就行，内置词典没被动过。
- `β θ χ`：希腊字母，数理材料里出现得多得多，走希腊字母读法（`θ` 读「西塔」）。
- `‖ ↑ ↓ → ↗ ↘ ⁿ`：各有本职读法（竖线、箭头、上标），走原读法。

- **ASCII 字母**（p b t d k g f v s z m n l r 等）：它们同时是最常用的英文字母，
  绝不能动。所以 `ʃɪp` 会读成「清龈后擦音 次闭前展唇元音 p」——前两个是音标，`p` 保持字母。
  真要让 ASCII 也按音标读，得加一个「音标模式」开关，目前没做。

## 引号

引号**不处理**，原样交给下游引擎。

一开始不是这样。弯引号被词典读成「左双引号」「右双引号」，一句对白要多出十个音节，
所以先改成统一读一个字「引」。后来定下的规矩更简单——连「引」也不读，理由是本项目的范围原则：
**只管下游读不出来的字符，别的一概不碰**。弯引号交给下游多半是安静的，比我们插一个字干净。

代价要说清楚：ASCII 的 `"` 和 `'` 会被下游引擎按它自己的规矩念出来，我们管不住。
这是明确接受的取舍——把它们收进词典，就等于又开始「处理」了。

引号和断句标点一起写进了 `NativePunctuation`：词典生成时收了它们直接报错，
运行时内置条目也一律忽略。**用户自定义词典不受限制**——你要让某个引号读什么，它就读什么。

同时退场的还有「词内撇号」规则。它当初存在的唯一理由，是不让 `don't` 里的撇号被读成「引」；
词典里没有引号条目之后它就成了死代码，留着反而会在你自己往词典里加引号读法时把你的选择吞掉。
## 带附加符号的字母

`é ñ ü ç`、拼音的 `mā má mǎ mà`、希腊语的 `ά` 原本原样透传给下游，
多数引擎读成基本字母或者干脆跳过——跳过意味着 `Ångström` 听起来只剩 `ngstrm`。

| 输入 | 简洁档 | 详细档 |
|---|---|---|
| `café` | cafe | caf e 锐音符 |
| `mǎ` | ma | m a 反折符 |
| `ά` | 阿尔法 | 小写阿尔法…… 锐音符 |

简洁档折成基本字母，详细档读出附加符号名。折出来的基本字母**还要再查一次词典**，
希腊字母才不会退化成一个乱码字符——所以 `ά` 简洁档听到的是「阿尔法」而不是一个怪字，
详细档则是词典里阿尔法的完整说明再接一句「锐音符」。

### 和音标怎么划界

同一个码位 `U+0301` 在 `café` 里是锐音符、在音标里是高平调。划界的办法是看**能不能合成**：

- `e` + `́` 能合成 `é`（U+00E9 真实存在）→ 正字法里的重音字母 → 折叠。
- `ɛ` + `̃` 合不出任何字符，Unicode 里没有「带波浪符的 ɛ」→ 音标的临时组合 →
  波浪符走词典读成「鼻化」。

这不是启发式，是 Unicode 规范化表本身的性质：正字法里真实存在的重音字母才有预组合码位，
音标的临时组合没有。代价是 `ẽ`（e 加波浪符）这类两边都成立的会被判成正字法字母——
日常文本里的葡萄牙语、越南语比音标多得多，而且详细档仍读得出符号名，用户词典还能逐条改。

## 自定义词典

内置词典打包在 assets 里改不了，所以用户的修改做成**叠加层**：用户条目排在内置条目
前面，同一个键上优先命中。「删除」一个内置读法，实际写入的是一条**屏蔽条目**——
内置词典永远保持原样，用户随时可以撤销。

设置里的「自定义词典」按三步走：

1. **查**：粘贴一个字符，或者写 `U+1F63B`。界面会同时报出「我的读法」和「内置读法」，
   这样用户知道原本读什么、自己改成了什么。
2. **改**：填简洁读法和详细读法，保存。保存后会直接跑一遍真实流水线，
   把「现在会读成什么」念出来——改完当场就能确认对不对，不用退出去试。
3. **导入导出**：走系统文件选择器，导出的文件在电脑上用记事本就能改。

### 词典文件格式

UTF-8，制表符分隔，`#` 开头是注释：

```
字符或码位 <TAB> 简洁读法 <TAB> 详细读法 <TAB> 选项
😻	猫猫头	猫猫头：一只笑眯眯的猫	kind=E
U+2705	对勾		kind=S
👍	-			← 简洁读法写一个减号 = 屏蔽，什么都不读
—	破折号		kind=S;repeat=collapse
Ω	欧米伽		kind=S;after_quantity=欧姆
```

- **第 1 列**两种写法都认：**字符本身**（推荐，可以直接粘贴，多码位序列如 `👨‍👩‍👧` 整串粘）
  或者码位（`U+1F63B` / `1F63B`，多码位用空格分开）。
  这里有个刻意的取舍：单个字母 `A`、`F` 本身就是合法的十六进制，所以要求裸码位至少两位，
  `A` 仍按字符走，想指定码位就写 `U+41`。
- **第 2 列**写 `-` 表示屏蔽。屏蔽**优先于详略档**——用户说不读就是不读。
- **第 3 列**留空表示与简洁读法相同。
- **第 4 列**可省略：`kind=E|M|P|S|B` 指定类别（不写则自动判定，只影响「关闭」档要不要丢弃）、
  `repeat=collapse` 连续重复只读一次、`after_quantity=欧姆` 这类上下文条件读法。

**每一行都是独立的**：某一行写坏了只丢那一行，并在导入时报出行号和原因，
不影响其余条目，更不会让引擎失声。同一个字符写了两遍只留第一条并报告。

词典文件落在**设备保护存储**里，和配置同一个地方——服务声明了 directBootAware，
开机解锁前就会被绑定，用户的自定义读法不能在锁屏时失效。

改动会推高一个版本号，服务在下一句合成时重建流水线，**不需要重启引擎**。
这一点很要紧：改完读法要立刻能听到效果，否则用户没法判断自己改对了没有。

## 配置为什么不会因为重启而丢

出过一次真实事故：**重启手机之后，下游引擎选择丢了**（当时还有个吞吐统计功能，
和配置存在同一个文件里，跟着一起没）。

根因是 `rememberGoodEngine` 每合成一句就写一次 SharedPreferences。`apply()` 每次都会
**重写整个 XML 文件**，而 TalkBack 一秒钟就有好几句——这个文件一直处在被反复整体重写的
状态。重启时进程被强杀，正好撞上其中一次重写，Android 回退到 `.bak`；万一 `.bak` 也在
半途，整个文件就空了。文件里的所有东西一起没。

三层修法：

1. **不再高频写。** `rememberGoodEngine` 只在值真的变了的时候才写；用户主动改的配置用
   `commit()` 同步落盘，不排进异步队列等着被杀。
2. **关键配置多存一份镜像。** `DurableStore` 先写临时文件、`fsync` 真正落盘、再原子改名，
   并把上一版留成 `.prev`。进程启动时（`App.onCreate`）如果发现 SharedPreferences 里缺了
   某个键而镜像里有，就补回去。**只补不覆盖**——镜像是兜底不是权威，用户刚改的值永远赢。

第 2 层是兜底：就算根因判断有偏差，只要配置还在镜像里，重启后就能自己长回来。
补回来的时候会在「检查朗读效果」的诊断行里说明，用户念出来就知道兜底生效了没有。

## 开机之后为什么会「设置全对但发声的不是我选的」

出过两次真实事故，症状一样，原因不同。

### 第一层：失败之后再也不重建

`ensureReadyInternal` 原来只要包名相同就复用已有的 `CountDownLatch`。第一次绑定失败之后
那个 latch 已经计数到零、`initOk` 是 false，后面每一次调用都拿到这个**已完成**的 latch，
`await` 立刻返回而 `initOk` 永远是 false——**引擎再也不会被重建**。

改成只有**还在进行中**的初始化才复用 latch，已经完成且失败的一律重建，
重建之间留两秒退避。现在的实现（`EngineSwitch`，见下文「换发声引擎为什么要等好一会」）
里每次失败都会按退避排一次重试，不存在「失败一次就再也不重连」。

### 第二层：框架会悄悄替你换一个引擎

修完第一层，症状**依然存在**：TalkBack 里选的是本应用、本应用里选的是 A、A 的进程也起来了，
连在本应用里点「试听」都还是系统默认的声音，重选多少次 A 都没用。

根因在 `TextToSpeech` 自己。公开构造函数 `TextToSpeech(ctx, listener, engine)` 是
**`useFallback = true`**，AOSP 的 `initTts()` 里：

1. 先连你点名的引擎；连不上**不报错**，继续往下；
2. 连「用户的默认引擎」；
3. 连「系统里排名最高的引擎」。

连上任意一个都返回 `SUCCESS`。开机未解锁那会儿 A 绑不上，框架就悄悄换成系统默认引擎并报成功，
我们信以为真。更糟的是 `initOk` 成了 true，快速路径此后一直返回成功，
**用户再怎么重选 A 都不会触发重连**——这正是「重设也没用」的原因。

修法是**构造 `TextToSpeech` 之前，先自己 `bindService` 一次目标引擎**，确认它此刻真的连得上。
这条只用公开 API。
（`getCurrentEngine()` 能直接读出实际连上的是谁，但它在公开 SDK 里是隐藏的，
只能反射，所以只拿它当第二道保险和诊断信息——读不到就不做判断，
绝不能因为「读不到」把一条本来能用的链路判死。）

这次探测的绑定要**一直留到新连接建好**才放。先放的话，没有别的客户端时下游服务会被销毁，
紧接着 `TextToSpeech` 再绑一次又得重新创建——重量级引擎等于冷启动两遍。

### 第三层：但连不上时**必须照样出声**

第二层最初写成「连不上就报错」，结果捅了个更大的娄子：**开机输密码那一刻完全没有语音**，
用户只能盲输密码。这比读错音色严重得多——锁屏时没有语音是安全事故。

所以最终的规则是：

- 目标引擎连得上 → 用目标引擎。
- 连不上 → **挑一个此刻能用的引擎顶上，照常出声**，标记为「兜底中」。
- 兜底期间后台一直盯着目标引擎：它绑不上时每两秒问一次包管理器（开机未解锁时，
  非 directBootAware 的引擎在包管理器里就查不到，所以这一步便宜），一旦查得到就去连，
  连好了下一句就换回去。这件事刻意不放在合成线程上做，那条线程每多等一毫秒都是朗读延迟，
  卡住更是全系统失声。
- 顶替候选一个都连不上时，**直接报错，不让框架自己挑**。框架的回退链（默认引擎、
  排名最高的引擎）用的是同一套解析规则，别的引擎都绑不上时，它唯一能绑上的就是我们自己——
  那是自己等自己的死锁，不是出声。早先这里是「仍旧点名目标，让框架接手」，现在改掉了。

一句话：**出声比出对的声重要。** 音色不对用户能忍几秒，没有声音他连密码都输不了。

诊断行里现在会念出「想连哪个、实际连上哪个」，兜底中还会明说「正在用顶替引擎发声，
可用之后会自动换回去」。

### 第四层：用着用着连接作废了

开源前体检时查出来的，还没在真机上撞到过，但场景很常见：下游引擎夜里被应用商店自动更新，
或者被强行停止。这时框架的绑定直接作废，`TextToSpeech` **不会自己重连**，之后每次提交都被拒。
而我们只在建连接时判一次「能不能用」，运行中没人把它改回「不能用」——结果是从那一刻起每句都没声音，
直到我们自己的进程重启。

现在提交被拒时，这条连接当场丢掉，重连（连不上就找顶替），这一句再试一次；
下游卡住十五秒没出声也同样丢掉，下一句换新连接。

## 开机后读到一半没声：系统把进程冻住了（原因在系统设置里）

症状：重启手机后头一两分钟里，读一条长一点的标题，读到两秒左右突然没声，
划一下屏幕又能继续；打开一次本应用之后就再也不出现。华为真机（HarmonyOS 4）。

**怎么确认是冻结而不是音频问题**：那句的音轨活了七秒，只吃进去 2.2 秒的数据，系统报
`restartIfDisabled ... disabled due to previous underrun`；临时加的一条每 250ms 醒一次的看门狗线程，
和卡在 `audioAvailable` 里的合成线程在**同一毫秒**一起醒来——只有整个进程被冻结才会这样。
解冻的时刻正好是读屏发来下一个 binder 调用的时刻。四次冻结都发生在开机后 109 到 118 秒之间。

**根因不在代码里，在华为的「应用启动管理」。** 本应用被设成「自动管理」时，开机后约两分钟
系统对没被用户打开过的应用做一轮冻结，本进程中招，冻到有人调它才醒。改成**手动管理**并打开
允许自启动、允许关联启动、允许后台活动，冻结就消失。

**每次卸载重装都会把这个设置清回自动管理。** 这就是它看起来像代码回归的原因：问题第一次出现在
换装正式版那天（签名不同，必须卸载重装），之后每次卸载重装都复发。把排查前后两个 APK 反编译逐项
对比，系统调用几乎没有差别；照着代码差异做的几个「修复」——预热完再换引擎、每五秒心跳、前台服务、
保留一条到自己的连接——要么无效，要么只是恰好和用户改设置的时机重合。全部撤掉了。

**现在的处理**：设置界面里有「检查系统的应用启动管理」一项，点它直接跳到手机管家里本应用的
那一页。重装之后记得去核对。

判据留给以后：怀疑冻结时，看合成线程被卡住的那次调用有多长，以及另一条线程是否在同一毫秒恢复；
两条线程一起醒，就是进程被冻，先去查系统的后台管理设置，别改代码。

## 换发声引擎为什么要等好一会（已修）

症状：在设置里把发声引擎从 A 换成 B，之后好几秒里读的一直是 A，
连「中转已就绪，将由 B 发声」这句确认都是 A 念的。

根因是上面第三层的规则分不清两件事。「手里有能用的引擎、但不是用户选的那个」，
可能是开机时目标暂时连不上，也可能是**用户刚换了引擎**——旧的 A 也「能用」。
两种情况走的是同一条路：先用着手里的，等后台每五秒一次的检查再换。
于是每次换引擎都要白等五秒以上，再加上连接本身的时间。

现在由 `EngineSwitch`（core 模块，纯逻辑）来管，这两件事分开处理：

- **刚选的引擎**：立刻去连，这一句**等它**。有旧引擎能顶着时最多等三秒，
  超时就先让旧引擎读这一句，连好了下一句再换。
- **这一轮已经连失败过的引擎**：合成线程不再等它，谁能出声就先用谁，重连交给后台。
  绑不上时每两秒查一次；连得上却起不来时，从两秒起每次翻倍，最多三十秒一次。
- **在设置里一选就开始连**：服务监听着这项设置，不等下一句话来。
- **换引擎只发生在两句之间**：只有合成线程会更换正在用的引擎，所以不会有哪一句读到一半被掐断；
  旧连接要等新的连好、换上之后才断开，换的过程中不会哑。

顺手去掉的几处拖慢：

- 连上新引擎时，如果正有一句在等它，就**不做预热**——预热那句「1 2 3」会排在真正要读的这句前面。
- 声音只在变了的时候才设。原来每一句都去查一遍下游的声音列表，谷歌这类引擎一次要带回几百个声音。
- 引擎列表直接问包管理器。原来是建一个 `TextToSpeech` 探针再调 `getEngines()`，
  那会顺手绑上系统默认引擎，它没在跑的话就平白被拉起来一次。

这些规则在 `core` 的 `EngineSwitchTest` 里逐条有测试（本机和 CI 都跑），
用假连接精确复现「新引擎连得慢」「新引擎坏了」「开机锁屏」「连到一半又换了」这些时序。
安卓那一层另有本机检查，拿去跑改之前的实现时，「换过去之后的第一句就该由 B 读」这一项会失败。

## 已知限制

- **只读符号，不读结构**。`∑` 的上下限、分式的分子分母、根号的作用范围、矩阵，
  都只把符号本身读出来，不描述结构。化学式同理：`H₂O` 读「H 下标 2 O」而不是「水」。
- **emoji 已全表重写**，1922 条基础序列覆盖全部 5209 条 emoji 词条。人工表内**重名 0 组**，
  再没有两个不同 emoji 读成同一个名字（起点是 11 组／42 处信息损失）。也**没有一条**
  再读占位名「表情符号」。
- 唯一的例外是有意为之：Unicode 17.0 把 👯 🤼 改写成了新的 ZWJ 序列，新老写法画的是
  同一幅图，所以**故意同名**——同一幅画换个编码就换个叫法，对听的人只有坏处。
  这两组在 17.0 里只定义了带肤色的形式、没有无肤色基础条目，靠 6 条手写基础条目兜住
  120 个肤色组合。
- **冷僻区块覆盖仍低**：乐谱符号、增补数学运算符（U+2A00–U+2AFF）里的生僻记号
  基本没收。它们在中文材料里罕见，按「宁缺毋滥」跳过了。
- 词典替换是**膨胀**变换，处理后的文本可能比原文长很多。分块逻辑已经考虑了这一点。

## 参与改进

读错了、漏读了，最有用的反馈是三样东西：**原文**（直接粘贴那个字符）、**现在读成了什么**、
**你觉得应该读什么**。在 Issues 里提就行。

改读法请改 `tools/data/` 下的表，再重新生成词典（见上文），不要手改 `symbols.tsv`。
提交前请跑一遍 `core` 的测试。

## 数据来源

emoji 的序列表与中文名来自 Unicode 官方数据（`emoji-test.txt` 17.0 与 CLDR 46.0.0），
适用 Unicode License。`tools/data/` 下的读法表随本仓库授权，其中：

- `symbols-braille.tsv`、`symbols-enclosed.tsv`、`symbols-boxdrawing.tsv`、
  `symbols-blocks.tsv` 由 Unicode 官方字符名**机械生成**，没有人工判断的余地，也就没有出错的余地。
- `symbols-ipa.tsv` 的盲文点位取自 [liblouis](https://github.com/liblouis/liblouis) 的
  `IPA.utb` / `IPA-unicode-range.uti`，**LGPL-2.1+**，2025 年版权方包含 IPA Braille 的
  作者 Robert Englebretson 本人。中文音理描述由该表注释里的英文描述用受控词表**机械翻译**
  （voiced uvular plosive → 浊小舌塞音），不经模型推断——音理描述错了对学音韵的人是误导。
- `symbols-emoji*.tsv` 由 Opus 5 分批生成，每批都过三道关：码位与字符逐条对照范围清单、
  简洁名长度、批内与**全局**重名（跨批撞名只有全局那道关能抓到，比如 🙋「举手」和
  ✋「举手」）。
- 其余几张表由模型生成后人工筛选订正，码位与字符的对应关系全部用 `unicodedata` 逐条校验过。
